## Rules and data sources

No weighted or numerical readiness score is produced. There are 14 evidence checks. Each is pass, attention or unknown; a dimension is attention if any of its checks needs attention, otherwise incomplete if any check is unknown, otherwise clear. Overall state follows the same precedence. The displayed pass count is simply the count of passing checks out of all checks, not a percentage, probability or interchangeable points. Unmodeled real-world contingency coverage always remains unknown, so present data cannot produce a fully-ready conclusion. The old plan health heuristic is untouched.

| Dimension | Actual checks |
| --- | --- |
| Budget (2) | Original Guardian warnings except missing-cost/unknown-expense imply attention; missing priced categories/unknown records imply incomplete pricing. Decimal projected/paid/committed/reserve figures come directly from the original summary. Known zero is a known cost. Retained cancelled obligations remain exposure. |
| Vendor (3) | Every saved group needs name/contact for the contact check; all groups need recorded booked status for the status check (any cancelled is attention); each needs a saved vendor quotation or a linked active expense quote/commitment for financial evidence. Saved quotes do not book a vendor, verify terms or become ledger expenses automatically. |
| Timeline (4) | Open non-event tasks strictly before the server date are overdue (today is not). Existing dependency validation checks missing/cyclic/unfinished/invalid ordering; no links means unknown, not proof of safety. Open planning milestones after the event or a passed event date need attention. Open or absent planning milestones mean incomplete progress. Completed work is not declared overdue. |
| Planning (3) | Saved event type/date/currency/headcount/title are available facts, not RSVP confirmation. Recorded unresolved decisions/assumptions mean incomplete evidence. Supplier checklist items must exist and all be completed for that check to pass. Empty optional requirements do not prove no requirements exist. |
| Resilience (2) | Current pending previews and stale/expired pending previews remain unreviewed; applied/discarded counts are evidence only. Top three action candidates use ordinal urgency, not scoring weights: known financial constraints, cancellations and dated/dependency failures first (priority 0); then missing/incomplete evidence (1); then reconfirm already-passing facts (2) if fewer than three gaps exist. Equal urgency preserves the documented check order in the table (budget, vendors, timeline, planning, resilience). Potential impact is qualitative and conditional, with no estimated money or fabricated deadlines. All other risks remain available in expandable dimension evidence.

## Boundary, API and refresh behavior

`POST /api/events/{event_id}/readiness` accepts only strict positive integer `revision` and optional strict boolean `explain` (default false). It returns revision/date/state, explanation, dimensions/check evidence, three actions with fixed destinations, source and limitations. It is read-only despite POST: no event, history, scenario, preference, plan-health or schema writes. Owner mismatch/absent event returns the existing 404; stale revisions use existing 409; invalid fields use existing 422; storage/proxy/body/rate/security/no-store behavior stays inherited.

A single SQLite deferred read transaction reads the owned event and its owned previews, avoiding mixed event/scenario snapshots. The snapshot may become old after another write; its revision and assessment day are explicit. There is no persistent readiness cache or migration. The response is an assessment at one point in time, not a lock on the workspace.

The existing Decision Engine gains `explain_readiness`: the shared separately instructed, bounded Gemini adapter receives only generated check IDs/statuses and candidate IDs/priorities, never theme, notes, contact details, incident text or user instructions. Strict output permits just revision and exactly three IDs. Unknown/duplicate/missing/stale IDs, extra fields, urgency inversion, oversized/malformed output or provider failure fall back to the original deterministic actions. All evidence, explanations, impacts, state and counts remain server-rendered; Gemini can only reorder the same candidates within urgency tiers. This is a deliberately constrained explanation/prioritization feature, not free-form AI risk analysis or a claim that prompt injection is solved.

The overview dashboard refreshes on saved-event changes, overview entry, scenario-list changes, visibility return and explicit refresh. Initial rendering uses offline calculation; the AI button is opt-in. Busy saves defer refresh; sequence/event/revision tokens reject obsolete asynchronous results. Old evidence clears during a pending/failed refresh. Errors expose no provider exceptions and show no success or write claim. A day rollover or external edit requires refresh/reopening; no live notification/polling promise is made. Links use existing workflow routes. No duplicated editor or apply endpoint exists.
